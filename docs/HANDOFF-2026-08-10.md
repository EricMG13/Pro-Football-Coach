## The one thing most likely to waste your time

**Three of the six P4 tuning attempts so far were fixing the harness, not the model, and each time
the harness was making the engine look wrong.** Before concluding the engine is off on a band,
check the instrument:

1. A favourite's win was counted as `winner == .home` — which measures home advantage twice and the
   favourite band not at all.
2. Every "mismatch" in the talent ladder was six rating points. A six-point favourite winning 53
   percent of the time is *correct*; `01` §6.5's 0.62–0.72 band describes real betting favourites.
3. `CalibrationRoster` gave every player on a team one skill ±6, so a twenty-point team gap made all
   twenty-three matchups favour the same side and the favourite won 94 percent. Real rosters are
   spiky, and the spikiness is most of what makes a game close.

All three are fixed. The pattern is not.

## What the current numbers mean

Six bands held before the last commit; five hold now, and the drop was deliberate. Commit `a629e86`
gave the run game a right tail and made it read `vision`, both of which `03` §1.1 and §1.2 require —
the constants were tuned around the old run model, so the tuned point moved when the model did. **A
worse-scoring correct model beats a better-scoring wrong one**, which is the same call `03` §5.2
makes about widening bands. Re-run the search; its space now includes the two tail constants.

Two couplings already observed, so you do not have to rediscover them:

- Cutting home advantage brings the pro home-win rate into band and pushes favourite-win *out*,
  because a per-matchup home bonus dilutes the talent signal.
- Flattening the talent curve to fix favourite-win breaks `03` §1.1's requirement that a ten-point
  gap matter more mid-scale than at the ends. The `Leverage` tests catch it — that is the spec
  defending itself against a calibration change, and it is working as intended.

**The remaining failures are concentrated where the model is thin, not mistuned.** There is no
per-drive accounting, and the play-caller is a named placeholder that P10 owns. More search over the
same constants will not fix those. Widen the model.

**D2's falsifier has not been met.** It fires if the model cannot hold every band simultaneously
"across 5 consecutive tuning attempts". Six attempts have happened; three were instrument repair and
one was a search rather than a hand pass. An instrument repair is not a failed tuning attempt. Do
not report the falsifier as met without counting honestly.

## Method notes worth keeping

- **Every phase's review found defects of one shape: capability the code declared and could not
  produce.** An enum case, a call-in trigger, a rules constant, a snap result — each looked
  implemented and was not. The defence that actually works is a test that enumerates the declared set
  and asserts every member is reachable, **with no exemptions**. `DriveEnding.endOfGame` was
  surviving on an exemption and was deleted instead.
- **A self-test that only tries the idealised spelling is not evidence.** The contract scans caught
  `import SwiftUI` and missed `import struct SwiftUI.Color`; caught `.hashValue` and missed
  `Hasher()`; caught `Date()` and missed `Date.now`. Any new scan owes a self-test over the
  *evasions*.
- **A round-trip test cannot see an ordering bug**, because `Set` and `Dictionary` iteration order is
  constant within one process. Only asserting encoded bytes or shape can. Two determinism bugs got
  through green suites this way.
- **Pin things as source literals.** A literal cannot be salted per launch, which makes it the
  cheapest cross-process assertion available. `SeedDerivation`'s golden vectors,
  `GenerationTests`'s world digest and `EngineTests`'s two play-by-play fingerprints all work this
  way. Every one of them has caught a real regression.
