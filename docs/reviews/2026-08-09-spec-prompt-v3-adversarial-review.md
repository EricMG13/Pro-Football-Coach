# Adversarial review — "Ground-Up Rebuild (v3): Research & Spec Package" prompt

Reviewed 2026-08-09 against the repo at `47ac105`. Target: the spec-author prompt addressed to
Fable 5, not the product. Every claim below is checked against a file in this repo or against the
prompt's own text.

**Verdict.** Structurally this is a strong brief — the authority tiers, the falsifier requirement
and gate-zero-first ordering are better scope control than most engineering specs get. But it
cannot execute as pasted, it makes three of its own gates unmeasurable, and it misreads the one
piece of evidence it leans on hardest. Fifteen or so edits fix all of it.

---

## Blocking — the prompt cannot run as written

### B1. All five owner parameters are blank, and §0 says stop

P1–P5 are placeholder text. §0: "If any parameter above is left blank, **stop and ask**." So the
only valid output of this prompt as pasted is five questions.

This is not pedantry, because the blanks are load-bearing in both directions:

- §4 demands gate zero be defended "against P4 with actual arithmetic" — P4 is the blank.
- §5 D5 says "Under P2, specify how the two systems differ" — P2 is the blank.
- Tier C strips authority from "all prior scope, platform and architecture choices", so P1 is the
  *only* source of stack truth, and it is a blank.

And §1 has already answered P2 on the owner's behalf: the mission is "college and pro". That
forecloses P2 option (c), "college-only v1 with pro as v2". Either the mission is provisional or
option (c) is dead — the prompt cannot hold both.

**Fix.** Fill P1–P5 before sending. Delete P2(c), or soften §1 to "college and/or pro per P2".

### B2. "Demonstrated in the simulator" is a gate the builder cannot reach

§7.8 defines done as "…the checklist satisfied and demonstrated in the simulator", and §8 says a
cold Opus 5 session reaches "done or a legitimate escalation" with zero conversational context.

The agent's execution environment has no iOS Simulator. This container: `swift` ABSENT,
`xcodebuild` ABSENT, Linux. `docs/STATUS.md` records the same thing historically and worse — the
Phase 4C session had no Swift toolchain at all, Ubuntu's archive carries only the unrelated
OpenStack "swift", and `download.swift.org` is refused by the org egress policy (403 on CONNECT).
That is precisely why Phase 4C shipped never having been compiled, and why STATUS.md carries the
line worth engraving on this brief:

> What stood in for the compiler was a multi-agent adversarial review… That catches a great deal
> and it is not the same thing as a build.

Simulator demonstration is an **owner** action on the owner's Xcode 26.6 machine. Writing it into
an unattended agent's definition of done guarantees one of two outcomes: a false claim of done, or
a permanent escalation on the last gate of every phase.

**Fix.** Split done in two. *Machine-verifiable* (agent asserts): build green, tests green,
calibration bands, cross-process determinism, soak — all headless, all achievable. *Owner-verifiable*
(agent hands off): simulator walkthrough against a written script. Make the hand-off script a
deliverable. State that an uncompiled surface must be labelled unverified in `STATUS.md`, as 4C was.

### B3. The per-phase UI gate is unmeasurable

§7.6 gates every phase on "touched surfaces auditing **≥17/20 with zero P0/P1** against the same
rubric that produced the 9/20 baseline."

That rubric does not exist in the repo. `docs/AUDIT.md:3`: "Generated by `/impeccable audit`
(native variant)". The five dimensions, their 0–4 anchors, and the P0–P3 severity definitions live
inside a tool. Meanwhile §10 restricts the builder to "named, already-approved skills" and never
names `/impeccable`. The gate therefore depends on an unnamed tool, or on nothing.

Second problem: the 9/20 baseline was a **whole-app** audit of 17 files. "Touched surfaces"
rescopes it, and two of the five dimensions don't survive that rescope — Adaptivity scored 2/4 for
"no orientation policy at all", and Platform Conformance for nav structure and large-title usage.
Those are global properties. A phase that touches three views cannot score them.

Third: ≥17/20 means losing at most 3 points across 5 dimensions, i.e. at least two dimensions at a
perfect 4/4 on every phase. Against a baseline whose best dimension was 2/4. That may be right as
an ambition, but it is asserted, not derived, and it is the gate that will stall the build.

**Fix.** Make `docs/AUDIT-RUBRIC.md` a deliverable: dimensions, 0–4 anchors, P0–P3 definitions,
verbatim from the tool. Name `/impeccable` as approved or replace the gate. Say how global
dimensions are scored per phase (suggestion: score them once per *milestone*, not per phase).

## Major — would produce a broken or self-contradicting package

### M1. Tier B misreads AUDIT.md, and the evidence that matters is never commissioned

Tier B calls `docs/AUDIT.md` "the empirical record of why the previous build failed."

It is not. Its own header (`AUDIT.md:3-9`) scopes it to `Sources/ProFootballCoachUI/` — 17 files —
and says "The engine (`FootballSimCore`) is out of scope, as are iPad, size classes and App Store
review." Its five dimensions are Accessibility, Performance, Appearance & Theming, Platform
Conformance, Adaptivity. Its executive summary says "The codebase is structurally sound and
idiomatic." It has a `## Positive Findings` section.

None of that measures whether the game is boring. The owner's diagnosis — "a bland application, not
a game" — is an **engagement** failure. The audit is silent on engagement. §3 half-concedes this
("corroborates the surface half"), then §8 makes dispositioning all 78 findings a condition of done
anyway.

The real cost is the omission this creates: **nowhere does the prompt commission evidence about the
actual failure.** No instruction to play the existing build. No session-length measurement. No
count of meaningful decisions per in-game week. No side-by-side of the current loop against FM
Mobile's on the very axis §4 says *is the game*. The build exists, runs, and has ten seasons of
soak behind it — this is the cheapest and most decision-relevant evidence available, and the brief
walks past it to go read forum posts about other people's games.

**Fix.** Add §6.0: *play the existing build*. Structured protocol — N in-game weeks, recording
decisions offered per week, wall-clock per week, the point at which the owner stops caring and why,
and which screens were opened versus which were skipped. That output is what §3 and §4 should be
argued from. Everything else in §6 is context around it.

### M2. The 78-finding disposition table is mostly ritual, and the findings have no IDs

AUDIT.md's findings are prose under severity headings (`### P1 — Major (24)`). They are not
numbered — a grep for any `F<n>` identifier returns zero. So "a disposition table where every
finding is…" requires the spec author to invent a 78-row ID scheme first.

Worse, Tier C discards all source and P1 may change the stack outright (the placeholder floats
SpriteKit). A large share of the findings are statements about code that will not exist:
"`Chip(filled:)`'s hard-coded white", "`JobOffersSheet` disables interactive dismissal",
"11 call sites do a synchronous save", "`ArcadeGameView` is dead code". Dispositioning those
individually yields 78 rows of "(i) structurally impossible in the new design" — budget spent,
nothing learned.

The transferable value is concentrated in `## Patterns & Systemic Issues` (`AUDIT.md:777`), and it
is genuinely excellent. Pattern 1 in particular is the single most reusable sentence in this repo:

> The defect is not ignorance of contrast; it is that the test's coverage boundary became the
> quality boundary.

That is a design principle for the rebuild, not a bug to close.

**Fix.** Require disposition of (a) all 25 P0/P1 findings and (b) all five systemic patterns —
each as a **standing invariant with a named test**, not a table row. Retire the P2/P3 tail in one
paragraph with a stated reason. Same protection, a fifth of the cost, and it converts findings into
tests rather than into prose.

### M3. New docs collide with old docs, and nothing retires the anti-canon

The prompt writes `docs/03-MATCH-ENGINE.md` and `docs/04-UX-AND-DESIGN-SYSTEM.md`. The repo already
has `docs/03-ARCHITECTURE.md` and `docs/04-SCREENS-UI.md`. The prompt never mentions either, nor
`docs/00-EXECUTIVE-PLAN.md`, nor `docs/06-PLAYED-GAME-MODE.md`, nor `docs/plans/*`.

§7.8 requires the build prompt to "name the canon as sole source of truth." But a cold Opus 5
session opening this repo reads `README.md`, which says **"Start here: docs/00-EXECUTIVE-PLAN.md"**
— a doc the new package never touches. And it finds `docs/06-PLAYED-GAME-MODE.md`, which specifies
in detail the exact thing the new mission forbids:

> **On the Field** | You *control* offensive snaps, kicks, returns on a live all-22 field

Tier C's "silence means rewrite" governs the spec author. It does not delete files from the
builder's working tree. Naming the canon is not enough when the anti-canon is still sitting at a
canonical path with a README pointing at it.

Also note: `03-MATCH-ENGINE.md` replaces the *number* of `03-ARCHITECTURE.md` but not its *job*.
D7 covers saves and D4 covers budgets, but module layout, engine/UI boundary enforcement, and
project structure have no home in the new deliverable set. That is a real gap, not just a
numbering one.

**Fix.** Add a deliverable: a doc manifest marking every pre-existing file SUPERSEDED-BY /
ARCHIVED-TO `docs/archive/` / RETAINED, plus a rewritten `README.md`. Nothing outside the manifest
may remain at a canonical path. Add an architecture doc or fold its scope explicitly into `03`.

### M4. `docs/PRE-DEPLOYMENT-CHECKLIST.md` cannot be "regenerated" — it doesn't exist

`grep -rn "PRE-DEPLOYMENT" --include=*.md .` returns nothing. §7.6 says "a regenerated
`docs/PRE-DEPLOYMENT-CHECKLIST.md`". There is no source to regenerate from — this looks like a
memory of a different project.

**Fix.** Say "author", and specify what it must contain. If a prior project's copy is the intended
template, name it.

### M5. `01-RESEARCH.md` is told to be extended and overwritten at the same time

Tier B: "prior research; extend it, don't silently drop findings." §7.1: `docs/01-RESEARCH.md` is
"§6 output."

§6's five obligations do not cover what the file actually holds: §A reference-app screen inventory,
§B the Achi Jones "Football Coach" lineage, §C and §H community signal mined from the App Store and
r/cfbsimulator, §D the owner's own working patterns, §F legal guardrails. Writing §6's output to
that path drops all of it — which Tier B forbids in the same breath.

Same collision, smaller, for `DESIGN.md`: §7.2 says "rewritten or superseded" (an unresolved
either/or), §7.4 puts the design system in a *different* file, and `CLAUDE.md:25` tells every
session "DESIGN.md … **Read before any UI work**". Two design systems, one instruction pointing at
the wrong one.

**Fix.** Either a new path for v3 research plus an explicit merge instruction, or a clause naming
§A–§H as carry-forward. Pick one home for the design system and archive the other by name.

### M6. `CLAUDE.md` contradicts Tier C for the entire job, and is patched last

`CLAUDE.md` currently states, as standing rules for every session:

- `:40` "**Tech stack (decided — don't relitigate)**" — Swift 5.10+/SwiftUI, iOS 17, no third-party deps
- `:50` "Fictional league: **32 teams, 2 conferences × 4 divisions × 4 teams**"
- `:9`  "College mechanics… **are replaced by** pro mechanics"

Tier C strips authority from "all prior scope, platform and architecture choices." P1 is an open
parameter. The mission puts college *back in*. All three lines are now false, and the third is the
exact inverse of the new mission.

The `CLAUDE.md` update is buried inside deliverable §7.6 — second to last. So every session between
now and then runs under standing rules that contradict the brief, and §7.8's "they must not
conflict" has no enforcement point because the conflict is resolved after both documents are
already in use.

**Fix.** Make the `CLAUDE.md` rewrite **deliverable zero**, before research starts. Until it is
rewritten, add an explicit line to the prompt: "`CLAUDE.md` has no authority over this brief where
they disagree."

### M7. D3's "~15 off-screen games" is a pro-only figure, and the mission includes college

32 pro teams → 16 games → 15 others. Correct. FBS is ~134 schools → ~65 games a week, before any
FCS tier the design chooses to model, and before recruiting AI and a transfer portal for 134
programs rather than free agency for 32.

D4 tells the author to derive performance budgets from D3. Deriving a week-advance budget from a
figure that is off by more than 4× on the college side, in a product whose mission statement is
"college and pro", produces a budget that is wrong in the direction that kills mobile builds.

**Fix.** State both figures. Derive D4 from the worse case. Add the recruiting/portal AI cost to
the week-advance budget explicitly — it is plausibly larger than the game simulation itself.

### M8. §9's ordering rules are circular

§9.1: "**§4 before everything.**" §9.2: research before positioning.

But §4 cannot be resolved well without §6.1 (what FM Mobile's in-match loop actually is, and what
it *removed* from desktop) and §6.2 (where DDS, Bound For Glory, Football Coach: College Dynasty
and Front Office Football each sit on precisely this axis, and what their communities say about
it). §6.2 is described in the prompt itself as "the highest-value signal available." As written,
the most consequential decision in the project is made before the research that informs it.

**Fix.** Reorder explicitly: §6.0 (play the build) + §6.1 + §6.2 → §4 → everything else. §9.1's
intent — *don't design the UI or engine before agency density* — survives intact.

## Moderate

### Md1. §3 asks the author to attack the diagnosis, and gives them nothing to attack it with

§3 is the best section in the brief. It is also unarmed. Analytics are forbidden by constraint
(offline, no analytics), P5 is solo dev plus agents so there is no playtest cohort, and nothing
instructs anyone to play the existing build. The author's only available sources are secondary
accounts of why FM players stay engaged. That yields a well-argued essay, which is exactly what §3
says it doesn't want. Fixed by M1.

### Md2. The burden of proof is asymmetric in the expensive direction

Tier C requires "a logged justification naming what would be lost by rebuilding" to **port**
anything. Nothing is required to **discard**. So the default is to throw away, and only keeping
costs you paperwork.

What is on the discard side of that asymmetry, per `docs/STATUS.md`: a calibrated engine with 224
tests and 13,226 assertions; ten-season soak invariants on ratings, ages, roster sizes, cap
legality, churn and save size; cross-process determinism including a bug that took real work to
find (`UUID.hashValue` is salted per launch, so the same seed produced a different league every
app start — invisible to any in-process test) plus a source-scanning test to stop it returning;
bounded save growth (8.3 MB → 2.3 MB after the free-agent pool and news feed were capped); and a
cap system hardened against practice-squad laundering.

Tier B says treat the calibration bands and soak methodology as reusable knowledge — then §6.4
orders the author to derive calibration targets from public sources from scratch, with no reference
to the bands already asserted in the test suite.

**Fix.** Make the discard log symmetric: for the engine specifically, require a written note on
what is lost. Rewrite §6.4 to start from the existing asserted bands and extend them — the genuine
gap is college, not pro.

### Md3. Falsifiers are required where falsification has no instrument

§5 demands "what evidence would falsify it" for all nine D-items. D1 (agency model), D8 (jeopardy)
and D9 (onboarding) are falsifiable only by watching a human play. P5 says solo developer plus AI
agents. Without a named instrument these will be written to satisfy the checklist.

**Fix.** Require each falsifier to name its instrument: soak assertion, calibration band, timing
harness, or *owner play-session protocol with a specific metric and a threshold*. The last is a
legitimate instrument at n=1 if the metric is stated in advance.

### Md4. The 130-snap figure is right; the arithmetic it feeds is underspecified

"~130 snaps" is sound as the count your team is on the field for (≈65 offensive, ≈65 defensive).
But the arithmetic §4 demands changes by 2× depending on whether the player calls defense too, and
college tempo pushes the number toward 150–180.

More importantly, the formula the prompt gives — snaps × seconds-per-decision × games — prices only
the decisions. It omits **presentation time**, which dominates: at 6 seconds of animation per snap,
130 snaps is 13 minutes of watching before a single decision is costed. A 2D match engine that
nobody watches is wasted work; one that must be watched blows P4 on its own.

**Fix.** Mandate the terms: snaps × (decision time + presentation time) × games, with offense-only
vs both-sides declared, college and pro computed separately, and an explicit skip/fast-forward
multiplier plus the expected share of games played at each fidelity.

### Md5. Tier A's "every constraint is a testable assertion" doesn't work for the legal guardrail

"Never copy protected expression" is not testable. What *is* testable and should be named: a
generated-name blocklist test (no team, city, school, conference, stadium, player or coach name
collides with a maintained list of real ones), and a colour-pair check against real trade dress.
`docs/01-RESEARCH.md` §F already holds the guardrail research to build this on.

**Fix.** Name the two tests. Keep the rest of the guardrail as a review checklist item, and say so
rather than pretending it is an assertion.

### Md6. §10 names tooling that may not exist, and omits the tool a gate depends on

`/deep-research` and "Claude Design via the briefs workflow" are named as required. Neither is
guaranteed present in the executing session. `/impeccable`, which B3's gate depends on entirely, is
not named at all — while §10 forbids anything not named. §10's supply-chain instinct is right; its
allowlist is incomplete.

**Fix.** List approved skills explicitly, including `/impeccable`. State the fallback when one is
unavailable: do the work manually and label the output as such, rather than stalling or improvising
a substitute.

### Md7. Four decisions are missing from the register

- **AI quality.** The coordinator and opponent AI is load-bearing under every D1 option except
  every-snap play-calling, and §6.2's own premise says community complaints are the best signal —
  in this genre those complaints are overwhelmingly about AI. No D-item owns it.
- **Test strategy under the real toolchain.** `STATUS.md` records that neither XCTest nor
  swift-testing ships with the Command Line Tools, so the suite runs as an executable target with a
  hand-rolled harness. §7.6 gates every phase on "tests green" without deciding what runs them, in
  an environment that has repeatedly lacked a toolchain entirely.
- **Accessibility contract.** The audit's worst dimension was Accessibility at 1/4, with Reduce
  Motion at 0 occurrences and 3 accessibility modifiers across ~140 KB of view code. The ≥17/20
  gate is unreachable without fixing it, yet no deliverable explicitly owns contrast tokens,
  Dynamic Type, Reduce Motion and VoiceOver as a contract with tests.
- **Content volume.** D6 asks for rivalries, traditions and conference politics. Nobody decides how
  many schools, name tables and archetypes are authored versus generated — the difference between a
  two-week and a two-month task for a solo developer.

### Md8. The build prompt's unit of work is too large to be one session

§7.8 asks for one prompt for "an unattended Opus 5 session… to build the game end to end", and §8
says it reaches done or escalation. A college-and-pro career sim with a 2D match engine is not one
session's work at any effort setting. There is no checkpointing, resumption or budget story — while
`CLAUDE.md` itself mandates "one phase at a time" with adversarial review at each phase end, which
§7.8 silently overrides. The "delegation cap" is required but left as a word, not a number.

**Fix.** Make `08` a *phase-entry* prompt with a resumption contract: read `05`, find the first
phase whose gates are not green, execute that phase only, run the phase-end review, stop. State the
delegation cap as a number. Then §8's "reaches done or a legitimate escalation" becomes true per
invocation instead of aspirational across the project.

## What is good and should survive editing

- **Authority tiers with "silence means rewrite."** The clearest scope-control device in the brief,
  and the thing that stops a rebuild silently becoming a refactor.
- **Falsifier plus reversal-cost on every decision.** Rare and correct.
- **§3's refusal to let the cure be assumed** — naming that FM Mobile is *itself* a menu-driven app
  is the sharpest observation in the document, and it is the one that most needs evidence behind it.
- **D3's consistency requirement as a hard requirement**, not an optimisation to find later. Two-tier
  sim divergence is exactly the bug that surfaces in season six and cannot be fixed cheaply.
- **§10's rejection of "explore GitHub for tools"** as a supply-chain surface.
- **Stable paths as the spec-author/builder interface contract.**
