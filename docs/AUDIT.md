# Native iOS Audit — Pro Football Coach

> **Evidence, never direction.** This audits the **prior build's** UI at commit `71a9d46` — a
> portrait app with a five-tab bar, on a design system this project does not inherit. Its value is
> the failure patterns it names (the coverage-boundary rule in `CLAUDE.md` comes from here); its
> recommendations are not instructions for the current build. Design authority:
> `docs/04-UX-AND-DESIGN-SYSTEM.md` for values and rules, the eight `*-v3.dc.html` sheets for
> composition and states (`04` §6.5), `docs/04b-AUDIT-RUBRIC.md` for scoring.

Generated by `/impeccable audit` (native variant) on 2026-08-09 against commit `71a9d46`.
Source-level audit of `Sources/ProFootballCoachUI/` — 17 files, ~5,500 lines. The engine
(`FootballSimCore`) is out of scope, as are iPad, size classes and App Store review.

Five dimension finders ran in parallel; every finding was then re-opened at its cited line by an
adversarial verifier instructed to refute it. **84 raised, 6 refuted, 78 confirmed.** The six
refutations are kept in an appendix, because what the audit got wrong is as useful as what it found.

## Platform Conformance Verdict

**Pass, with real violations.** This does not read as a ported website. Navigation is a stock
`TabView` of five genuine sections over `NavigationStack`s; controls are stock `Toggle`, `Stepper`,
`Slider`, `Picker`, `swipeActions`, `alert`, `sheet`; iconography is SF Symbols throughout; there is
no hand-rolled global nav and no hover-dependent affordance. A fluent iPhone user would trust most
of it.

Where it breaks the platform, it does so in specific, fixable ways rather than in its bones:

- **Large titles on every pushed detail screen** and on six of eight modals — the HIG reserves them
  for top level, and using them everywhere flattens the hierarchy they exist to signal.
- **Four sheets put "Done" in the leading cancellation slot**, and the arcade puts an *irreversible*
  "sim the rest of the game and commit it" action there. Leading is where users expect Cancel.
- **`JobOffersSheet` disables interactive dismissal and ships no dismiss control** — a genuine trap.
- **Touch targets**: chip-as-button filter bars are ~21pt tall and 6pt apart; `.controlSize(.small)`
  shrinks the Draft and Hand Off buttons to ~28pt; the matchup-preview entry point is a ~16pt caption.
- **Ten hard-coded `.system(size:)` values, four below the 11pt floor.**
- **No Settings surface exists at all**, so the Light/Dark/System control that `docs/04-SCREENS-UI.md`
  §20 specifies is absent — the app cannot be put into a chosen appearance.

## Executive Summary

- **Audit Health Score: 9/20** (Poor — major overhaul)
- **78 confirmed issues**: 1 P0, 24 P1, 36 P2, 17 P3
- The codebase is structurally sound and idiomatic. The score is low because two commitments the
  project wrote down for itself — measured contrast, and Reduce Motion — are unimplemented almost
  everywhere outside the one system that was tested.

**Top five:**

1. **[P0] Every league mutation blocks the main actor on a 2.4–3.3 MB save.** Encode, backup copy,
   atomic write and directory rescan, synchronously, at 11 call sites. Advancing a week, making a
   pick, or a single scouting action all pay it — and the Draft Board pays it twice per action.
2. **[P1] Contrast fails at 50+ sites in four independent forms** — `Chip(filled:)`'s hard-coded
   white (1.41–4.13:1), tinted chips built from raw system colours (1.41–3.44:1), headline figures in
   raw `.green`/`.red`, and white labels on the team tint in dark mode (2.65–2.90:1). The hero band
   fails for **all 32 teams**.
3. **[P1] Reduce Motion is never checked** — zero occurrences in the entire UI layer, against an
   explicit commitment in both `PRODUCT.md` and `DESIGN.md`.
4. **[P1] Nineteen fixed-width frames wrap Dynamic Type text**, truncating the primary number on
   roster and standings rows at large sizes.
5. **[P1] The app declares no orientation policy**, so every portrait screen rotates into a broken
   landscape — and the one screen actually specced as landscape loses its controls when it does.

## Detailed Findings by Severity

### P0 — Blocking (1)

**Every league mutation performs a 2.4–3.3 MB synchronous JSON encode, backup file copy, atomic write and directory rescan on the main actor**

- **Location**: `Sources/ProFootballCoachUI/AppState.swift:164` — 11 sites
- **Category**: Performance
- **Impact**: `mutate` funnels every state change into `autosave()` → `persist()` → `SaveStore.save`, which encodes the whole `League` with `JSONEncoder.stable()` (`.sortedKeys`), copies the previous save to a backup, writes atomically, and then re-enumerates and re-decodes every meta file via `saves = store.list()`. Measured full `SaveStore.save()` cost: 84 ms for a 2.43 MB save at week 11, 112 ms for a 3.29 MB save at the playoffs — all on the main actor, all with no loading state (`isBusy` at AppState.swift:42 is declared and never read or written anywhere in the UI layer). Several user actions pay it more than once: `advanceWeek` mutates then calls `refreshGoals`, whose `guard` sits *inside* the mutate closure (line 187) so the closure always reassigns and always saves — 160 ms of disk I/O measured for one "Sim Week", on top of 105 ms of engine work. `advanceOffseasonStage` saves 2–3 times; `completeDraftStage` saves up to 5. Nothing in `Sources/ProFootballCoachUI` ever leaves the main actor (no `Task.detached`, no `await`, no `.task`) other than the three arcade timer loops.
- **Guideline**: PRODUCT.md line 45: "Performance and durability targets that shape design: week advance under 150 ms, saves under 5 MB". A single week advance measures ~265 ms (105 ms sim + 160 ms of double autosave) and misses the stated budget on the save alone.
- **Recommendation**: Debounce/coalesce autosave (one write per user action, not one per mutation), move the encode + write off the main actor onto a serial background executor, and stop calling `store.list()` from `persist()` — the save-list only needs refreshing when the menu is shown. Move the `guard !league.seasonGoals.isEmpty` in `refreshGoals` outside the `mutate` closure so a no-op goal refresh does not trigger a second 2.4 MB write.
- **Suggested command**: `/impeccable optimize`

### P1 — Major (24)

**Reduce Motion is ignored everywhere — zero checks in the entire UI layer**

- **Location**: `Sources/ProFootballCoachUI/Features/ArcadeGameView.swift:123` — 3 sites
- **Category**: Accessibility
- **Impact**: A user with Reduce Motion on still gets the ball sliding across the arcade field on every play (0.35s ease), the wizard step pill stretching, and the tutorial page sliding. For vestibular-sensitive users the arcade ball animation fires once per snap for an entire game.
- **Guideline**: DESIGN.md:182 "Honour Reduce Motion on every transition and celebration." PRODUCT.md:82 "Reduce Motion honored on every transition and celebration." Apple HIG — Motion.
- **Recommendation**: Add `@Environment(\.accessibilityReduceMotion) private var reduceMotion` at each of the three sites and gate: `.animation(reduceMotion ? nil : .easeInOut(duration: 0.35), value: ballFraction)`; `.animation(reduceMotion ? nil : .snappy, value: current)`; `if reduceMotion { page += 1 } else { withAnimation { page += 1 } }`. A shared `.motionAware(_:value:)` modifier in DesignSystem.swift would keep it token-shaped.
- **Suggested command**: `/impeccable harden`

**Fixed `.frame(width:)` around scaling text truncates the primary number on 19 rows**

- **Location**: `Sources/ProFootballCoachUI/Features/TeamViews.swift:236` — 19 sites
- **Category**: Accessibility
- **Impact**: At accessibility text sizes subheadline reaches roughly 42pt, so a two-digit overall needs ~50pt of width and gets 32pt — every roster row renders "9…" instead of "99". LiveGameView.swift:255 is worse: `.title3` in a 40pt box holds a final score. LeagueViews.swift:39 gives a 46pt box to a record string like "12-4-1". The number the row exists to communicate is the first thing to disappear.
- **Guideline**: DESIGN.md:136 "Every screen must survive XXXL without truncation or overlap." PRODUCT.md:76 "Every screen survives Dynamic Type at XXXL without truncation or overlap."
- **Recommendation**: Replace fixed widths with `@ScaledMetric(relativeTo: .subheadline) private var ratingColumn: CGFloat = 32` so the gutter grows with the type, or drop the frame and use `.layoutPriority(1)` plus `Spacer(minLength:)` for alignment. Add a `Layout` token for the two recurring gutters (rating column, record column) so the fix is one place, per DESIGN.md:178.
- **Suggested command**: `/impeccable harden`

**White chips on the team gradient measure 2.77–4.08:1 — below AA for all 32 teams**

- **Location**: `Sources/ProFootballCoachUI/Features/TeamViews.swift:58` — 9 sites
- **Category**: Accessibility
- **Impact**: `Chip(color: .white)` draws full-strength white 11pt semibold over a 14% white wash, which lightens the gradient underneath it. Measured against the actual composited surface: SF Fog (#5C6B73) reaches 2.77:1 at the gradient's middle stop and 4.08:1 at its darkest; every one of the 32 teams measures 3.87:1 at the bottom-trailing stop, because `.black.opacity(0.55)` composited over the #F2F2F7 page is mid-grey, not black. Team record, reputation, stadium, coach level, and career trophy counts are all delivered through these chips.
- **Guideline**: DESIGN.md:113 The Measured-Surface Rule — "A colour is verified against the surface it is actually drawn on … not against an idealised white." PRODUCT.md:77 "4.5:1 contrast for text in both light and dark themes, verified against the actual surfaces a value is drawn on."
- **Recommendation**: Either make hero chips filled with a solid opaque scrim (`Capsule().fill(.black.opacity(0.35))` under white text) instead of a 14% white wash, or make `TeamTheme.gradient` composite over an opaque dark base rather than relying on `.opacity()` over the page. Then extend DesignSystemTests.swift — the existing suite (lines 74-92) checks the rating ladder against card/page/chip but never checks white-on-gradient, which is why this passed.
- **Suggested command**: `/impeccable harden`

**"Kick Off the Season" CTA is white-on-white at 2.48–4.03:1**

- **Location**: `Sources/ProFootballCoachUI/Features/SeasonHubView.swift:106`
- **Category**: Accessibility
- **Impact**: `.borderedProminent` draws a white label on its tint. Tinting it `.white.opacity(0.22)` puts white text on a 22%-white fill over the gradient: 2.48:1 for SF Fog, 3.09:1 San Antonio, 4.03:1 for the darkest team in the league. No team clears 4.5:1. This is the only control on the preseason card and the gate into every season.
- **Guideline**: PRODUCT.md:77 "4.5:1 contrast for text in both light and dark themes." DESIGN.md:190 "Don't reach for a raw system colour as text on a card without measuring it first."
- **Recommendation**: Use an opaque scrim rather than a translucent white: `.tint(.white)` with `.foregroundStyle(theme.primary)` (a solid white button with the team colour as label), or a solid `.black.opacity(0.35)` fill with a white label. Measure whichever you pick against all three gradient stops.
- **Suggested command**: `/impeccable harden`

**The on-field aiming surface is a bare drag gesture with no accessibility element**

- **Location**: `Sources/ProFootballCoachUI/Features/ArcadeFieldView.swift:191`
- **Category**: Accessibility
- **Impact**: The whole "On the Field" mode — receiver positions, the line to gain, the trajectory arc, the aim reticle — is drawn as shapes with no labels and driven by an unlabeled `DragGesture` on a `.contentShape(Rectangle())`. VoiceOver's cursor finds nothing on the 300pt field. A VoiceOver user's only operable action during a live snap is "Hand Off" (line 398), so an entire advertised game mode collapses to one button.
- **Guideline**: PRODUCT.md:74 "native iOS accessibility as a construction requirement rather than an audit item." Apple HIG — Accessibility: gesture-only interactions need an accessible alternative.
- **Recommendation**: At minimum: label the field container and expose the state as a value (`"Field. \(model.receivers.count) receivers. \(ordinal(situation.down)) and \(situation.distance)."`), make each `ReceiverTarget` dot an element labelled `"\(receiver.position.abbreviation), \(Int(receiver.depth)) yards"`, and add `.accessibilityAction(named:)` entries — one per receiver — that call `model.throwBall(atDepth:lateral:)` with that receiver's coordinates so the mode is playable without the drag.
- **Suggested command**: `/impeccable harden`

**Stat and standings rows read as loose fragments, not sentences**

- **Location**: `Sources/ProFootballCoachUI/Features/LiveGameView.swift:286` — 5 sites
- **Category**: Accessibility
- **Impact**: `comparisonRow` puts three separate `Text` views in an HStack, so VoiceOver reads "312" … "Total yards" … "289" as three disconnected elements in visual left-to-right order, with no indication which team owns which number. `quarterRow` is worse — the quarter-points `ForEach` produces "7" "3" "14" "0" then "24" with no quarter labels at all. The attributes grid emits 2N elements, each number spoken before the attribute it belongs to. This is verbatim the failure both docs name.
- **Guideline**: DESIGN.md:181 "Give every stat row a VoiceOver reading that is a sentence, not nine loose numbers." PRODUCT.md:79 "a box-score row reads as a sentence, not nine loose numbers."
- **Recommendation**: Add `.accessibilityElement(children: .ignore)` plus a composed `.accessibilityLabel` on each row builder, e.g. comparisonRow → `"\(label): \(away?.abbreviation ?? "Away") \(awayValue), \(home?.abbreviation ?? "Home") \(homeValue)"`; quarterRow → `"\(team.abbreviation), \(stats.points) points. By quarter: " + stats.quarterPoints.enumerated().map { "Q\($0+1) \($1)" }.joined(separator: ", ")"`; attributes grid → label each cell `"\(attribute.displayName) \(value), \(RatingTier(rating: value).label)"`. Same treatment for the standings row and box-score row.
- **Suggested command**: `/impeccable harden`

**Chip-as-button filter and scouting controls are ~21pt tall, 6pt apart**

- **Location**: `Sources/ProFootballCoachUI/Features/FrontOfficeViews.swift:479` — 4 sites
- **Category**: Accessibility
- **Impact**: `Chip` is caption2 (~13pt line) plus 4pt vertical padding = roughly 21pt tall — under half the 44pt minimum. The three scouting-action buttons sit 6pt apart in an HStack, so "Narrow", "Reveal Potential" and "Full Report" are crammed adjacent targets that each spend scouting points irreversibly. The same pattern gates the free-agency and draft position filters and the statistics category switcher.
- **Guideline**: PRODUCT.md:78 "44pt minimum touch targets." DESIGN.md:142 "List rows target a `52` height, comfortably above the 44pt touch minimum" — the chip buttons ignore that floor. Apple HIG — Layout, 44×44pt minimum.
- **Recommendation**: Add `.frame(minHeight: 44)` plus `.contentShape(Rectangle())` to the Button (not the Chip — the pill should stay visually small), and widen the scouting HStack spacing from `Layout.tight` to `Layout.small`. Consider `.buttonStyle(.borderless)` with explicit `.padding(.vertical, 12)` so the tap slop is real without changing the pill's drawn size.

**Record Book aggregates every player's career and season stats inside the view body**

- **Location**: `Sources/ProFootballCoachUI/Features/LegacyViews.swift:94`
- **Category**: Performance
- **Impact**: `RecordsBook.current(in:)` walks 9 record kinds × 32 teams × 69 players and folds `league.results` (and `league.history`) for each one. Measured on a release build against a real generated league: 349 ms at week 11 (148 results), 656 ms at the Wild Card round (272 results). An iPhone is meaningfully slower than the Mac these numbers came from. Tapping "Record Book" from the Coach tab therefore freezes the UI for over half a second in season one, and the cost grows every season because `careerStats` also folds `league.history`. It re-runs on every body pass, so any AppState change while the screen is open pays it again.
- **Guideline**: PRODUCT.md "Performance and durability targets that shape design" — the app is specified to stay responsive across ten simulated seasons; this path degrades monotonically with season count. Apple HIG (Responsiveness): work that blocks the main thread past a frame budget needs backgrounding or progress feedback.
- **Recommendation**: Compute the record book once per season transition (or on a background task with a loading state) and cache the result on the league / AppState, rather than calling `RecordsBook.current` from inside `List`'s content builder. At minimum, hoist it into an `@State` populated by `.task` so it runs once per appearance instead of once per render.
- **Suggested command**: `/impeccable optimize`

**StatsView recomputes season stats for all 2,208 players, twice per render**

- **Location**: `Sources/ProFootballCoachUI/Features/ArcadeGameView.swift:274` — 2 sites
- **Category**: Performance
- **Impact**: `leaders` loops all 32 teams × 69 players and calls `league.seasonStats(for:)`, which reduces over the entire `league.results` array for each player. Measured: 40 ms per pass at week 11, 74 ms at the playoffs. The property is referenced twice in `body` — `leaders.isEmpty` at line 237 and `ForEach(Array(leaders.enumerated())…)` at line 242 — so a single render costs 79 ms mid-season and 148 ms at season end, doubling again if the body re-evaluates. Every tap on a category chip (line 227) re-runs the whole scan, so the filter row feels broken on a phone. Each `Leader` also copies the full `Player` struct (including its ratings dictionary).
- **Guideline**: none (no DESIGN.md or HIG rule; this is a straightforward expensive-aggregation-in-body defect)
- **Recommendation**: Cache the per-player season totals once — fold `league.results` into a `[UUID: StatLine]` a single time and index it — and store `leaders` in `@State` keyed on `category`, so switching categories re-sorts a precomputed array instead of rescanning the league. At minimum, bind it to a `let` once inside `body` so it is computed once rather than twice.
- **Suggested command**: `/impeccable optimize`

**Opening a save parses the file twice and then immediately re-encodes and rewrites it**

- **Location**: `Sources/ProFootballCoachUI/Persistence/SaveStore.swift:153` — 2 sites
- **Category**: Performance
- **Impact**: `SaveMigrator.migrate` runs `JSONSerialization.jsonObject` over the whole file purely to read one `version` integer, then hands the same `Data` to `decoder.decode`. Measured: 23 ms + 136 ms at week 11, 31 ms + 207 ms at the playoffs. `AppState.load` (AppState.swift:122) then calls `persist()` unconditionally, re-encoding and rewriting the 2.4–3.3 MB file that was just read — another 84–112 ms. Total blocking main-actor cost to open a franchise: roughly 250–350 ms on a Mac, worse on device, with the last third of it doing nothing. The user taps a save row and the sheet sits frozen before dismissing.
- **Guideline**: Apple HIG (Responsiveness / Launch): opening content should not block the main thread; long operations need progress or backgrounding.
- **Recommendation**: Read only the version prefix (or store the version in the existing `.meta.json` sidecar, which is already decoded cheaply) instead of full-file `JSONSerialization`, and drop the `persist()` on line 122 of AppState.swift — loading a save does not change it. Perform the decode on a background task with the existing (unused) `isBusy` flag driving a loading state.
- **Suggested command**: `/impeccable optimize`

**Power Rankings builds 32 unvirtualized rows and computes each team's overall rating three times**

- **Location**: `Sources/ProFootballCoachUI/Features/LeagueViews.swift:61` — 3 sites
- **Category**: Performance
- **Impact**: `Team.overallRating` is not a stored value — it fans out to 11 `unitRating` calls, each of which runs `activeRoster` (a 69-element filter), a position filter, a `Dictionary(uniqueKeysWithValues:)` build, a `Set(chart)` build and a sort. Measured at 0.122 ms per call. The `ranked` computed property calls it for all 32 teams, then each row calls it twice more — `Format.rating(row.team.overallRating)` at line 94 and `.ratingStyle(row.team.overallRating)` at line 96 — so 96 calls per render. Measured 12.2 ms per body pass, and the `ForEach` at line 78 sits in a plain `VStack` inside `.card()` so all 32 rows are built eagerly with no virtualization. Line 89 additionally re-reads `app.league` and recomputes `record(for:)` per row rather than using the record already fetched in `ranked`. This card is on the Season Hub, which re-renders on every AppState change.
- **Guideline**: none (expensive recomputation in body; the collection size itself is bounded at 32 so eager rendering alone would be acceptable)
- **Recommendation**: Have `ranked` carry the already-computed rating and record through to the row (the tuple already has a `score` field going unused in the row body) so `overallRating` is computed once per team instead of three times, and cache `ranked` in `@State` refreshed on league change rather than recomputing it in `body`.
- **Suggested command**: `/impeccable optimize`

**Chip(filled:) hard-codes Color.white; white-on-fill measures 1.41–4.13:1 at every call site**

**TeamTheme.gradient uses translucent stops that composite over the page — hero text drops to 3.31:1 in light mode**

- **Location**: `Sources/ProFootballCoachUI/Theme/DesignSystem.swift:129` — 8 sites
- **Category**: Appearance & Theming
- **Impact**: Two of the three gradient stops are translucent, so the band's actual colour depends on `Color.pageBackground` behind it — #F2F2F7 in light, #000000 in dark. The middle stop (`primary.opacity(0.75)`), which is where the hero heading and chips sit, resolves to #4799A2 for the teal franchise (#0E7C86) in light mode: white heading text on it measures 3.31:1, and three more teams land between 4.39 and 4.88. **White labels on Color.accentColor / theme.tint measure 2.65–2.90:1 in dark mode**

- **Location**: `Sources/ProFootballCoachUI/Features/TutorialView.swift:105` — 6 sites
- **Category**: Appearance & Theming
- **Impact**: `RootView.swift:20` sets `.tint(app.theme.tint)`, and `tint` is deliberately lifted toward white in dark mode until it clears 4.5:1 as a *label*. - **Location**: `Sources/ProFootballCoachUI/Features/LeagueViews.swift:149` — 2 sites

- **Category**: Performance
- **Impact**: `visiblePlays` returns `Array(record.plays.prefix(…))`, copying up to ~130 `PlayEvent` structs. ## Patterns & Systemic Issues

**1. Contrast was measured exactly where it was tested, and nowhere else.** `DesignSystemTests`
verifies the five rating tiers and all 32 team tints against real composited surfaces — genuinely
rigorous work. Every surface the suite does not look at fails: filled chips, tinted chips from raw
system colours, gradient hero text, white-on-tint, `.tertiary` as body text, `.yellow` trophies at
1.51:1. The defect is not ignorance of contrast; it is that the test's coverage boundary became the
quality boundary.

**2. Token bypass at scale.** 43 literal spacings, 25 literal radii, 9–10 hard-coded font sizes and
3 off-scale radii, against `DESIGN.md`'s own rule that "a literal in a view is a defect".

**3. Written-down commitments with zero implementations.** Reduce Motion: 0 occurrences. VoiceOver:
3 accessibility modifiers in ~140 KB of view code, 0 `accessibilityElement` calls. Both are stated
as requirements in `PRODUCT.md` and `DESIGN.md`.

**4. Persistence is synchronous and over-eager.** The main-actor save is P0 on its own, and opening
a save parses the file twice then immediately rewrites it.

**5. The arcade layer is the weakest area** and partly unreachable: `ArcadeGameView` is dead code —
its only gate, `arcade && !isFinished`, is statically false because the single call site passes
`arcade: false`. Worth deleting or wiring up deliberately.

## Positive Findings

- No icon-only unlabeled buttons anywhere in the UI layer — every icon-bearing control uses `Label(title, systemImage:)` (SeasonHubView:159, 171, 201; DraftDayView:183, 191, 199, 209; LiveGameView:159, 165; CoachViews:369, 399, 412, 421; ArcadeGameView:158, 165, 174; TeamViews:483; ArcadeFieldView:282, 289, 332, 340) or pairs the glyph with adjacent text inside the same Button (RootView:144-159, TeamViews:108-117, FrontOfficeViews:105-114, CoachViews:167-177). This is the single most common VoiceOver defect in SwiftUI apps and it is entirely absent here.

- The rating ladder is genuinely rigorous and machine-verified, not asserted. DesignSystemTests.swift:74-92 checks all five tiers against the card, the page, AND the composited 14% chip tint in both themes at 4.5:1; lines 60-72 catch a typo'd hex before it can silently fall back to grey; lines 97-104 assert tier words are unique and non-empty. `runTeamTintTests` (113-148) does the same per-team for all 32 dark-mode tints against the exact wash a bordered button paints. The comment at DesignSystem.swift:150-153 records why `.green`/`.orange` were rejected (2.2:1 measured). This is better colour discipline than most shipping apps.

- Never-Colour-Alone is genuinely honoured for ratings in the non-button case: the tier colour is always painted on top of the number itself, never on a bare swatch, and `RatingTier.label` (DesignSystem.swift:171-181) is deliberately a word rather than a letter grade, with the reason documented (Potential already owns A+…F). At the ten `.ratingStyle()` sites outside a Button label the design works exactly as specified.

- Stock SwiftUI controls throughout — Toggle, Stepper, Slider, Picker, ProgressView, EditButton, swipeActions, alert, sheet, TabView — so all their built-in VoiceOver traits, values and rotor support come free. DESIGN.md:169 names reinventing these as "the most common form of native slop" and the code holds the line.

- `.contentShape(Rectangle())` applied deliberately to widen hit areas at 9 sites, with the reason written down at FrontOfficeViews.swift:199 ("Without this the gap between the name and the price is not tappable"). Someone was thinking about touch reachability even where the target sizing was missed.

- `monospacedDigit()` applied consistently to every figure that changes — ~25 sites across ratings, scores, clocks, cap figures and stat columns. This is a real low-vision aid, not just polish: digits that reflow between rows are far harder to scan.

- `EmptyStateView` on every list that can be empty (7 sites: InjuryReport, NewsFeed, Schedule, DraftBoard, SeasonGoals, History, HallOfFame, TrophyRoom) so a VoiceOver user never lands on silent blank space with no explanation.

- The arcade playbook and carrier buttons already specify explicit `minHeight: 44` / `minHeight: 46` (ArcadeFieldView:271, 284, 291, 334, 342) — the one part of the app where touch-target sizing was consciously enforced, and it happens to be the most time-pressured screen.

- `TeamBadge` uses `.minimumScaleFactor(0.6)` (NewFranchiseWizard:289) so the mark degrades gracefully rather than clipping — the right pattern, just not applied at the other fixed-box sites.

- Two of the arcade's custom bars did receive `.accessibilityLabel` (ArcadeFieldView:328, 412). Incomplete, but evidence of intent rather than indifference — and a natural place to extend rather than start from nothing.

- List virtualization is broadly correct where it matters. Every genuinely large collection is inside a `List`: DepthChartView's 69-man roster (TeamViews.swift:127), ContractsView (FrontOfficeViews.swift:122), FreeAgencyView (FrontOfficeViews.swift:160), DraftBoardView's 304-prospect class (FrontOfficeViews.swift:446), DraftDayView's board (DraftDayView.swift:73), StatsView (ArcadeGameView.swift:222) and the live play-by-play (LiveGameView.swift:85). The unvirtualized `VStack`+`ForEach` cases are all deliberately bounded — 32 teams, 40 news items, ~17 games.

- Unbounded data is explicitly capped before it reaches the view. `DraftDayView.available` prefixes the board to 40 rows (DraftDayView.swift:225) and `NewsFeedCard` takes `.suffix(40)` (LeagueViews.swift:111). Someone thought about growth in those two places.

- `SaveStore.list()` decodes only the small `.meta.json` sidecars (SaveStore.swift:79-92) rather than the 2.4 MB league files, so the Load Franchise sheet renders without touching a single full save. This is exactly the right shape and should be preserved when the rest of persistence moves off the main actor.

- `TeamBadge` is initialised from `abbreviation` + `primaryHex`, never the whole `Team` (NewFranchiseWizard.swift:294-302), so a badge in a 32-row list does not retain a 69-player roster and does not invalidate when the roster changes. The geometric logo is a `Circle` plus a `Text` — no image decode, no cache to warm, no asset catalogue. The stated no-image-assets constraint is delivering a real performance benefit here, not just a legal one.

- The flat-by-construction design system costs nothing to composite. DESIGN.md's zero-shadow rule is honoured throughout, surfaces come from `secondarySystemGroupedBackground` / `systemGroupedBackground` (DesignSystem.swift:246-260), and there is no blur, no `.drawingGroup()`, no offscreen-rendering trigger anywhere in the layer.

- `PlayerCardView.attributes` uses `LazyVGrid` (TeamViews.swift:441) and `TrophyRoomView.trophyCase` does too (LegacyViews.swift:229) — the grids that could grow are lazy even though the current data is small.

- The arcade's ball motion is declarative rather than timer-driven (`.animation(.easeInOut(duration: 0.35), value: ballFraction)`, ArcadeGameView.swift:123), and `TrajectoryArc.path` builds a fixed 28-point path with no allocation churn (ArcadeFieldView.swift:502-518). The per-frame problem is the observation scope, not the drawing.

- Zero shadows in the entire UI layer — `grep -rn "\.shadow("` over Sources/ProFootballCoachUI returns nothing. The Flat-Forever Rule is genuinely honoured, not just documented.

- The rating ladder is a real adaptive token set: RatingTier (DesignSystem.swift:158-204) ships light/dark hex pairs, and Tests/SimTests/Suites/DesignSystemTests.swift:74-92 asserts ≥4.5:1 for every tier against the card, the page AND the 14% chip wash in both themes — reading the shipped hexes rather than a copy. DesignSystemTests.swift:60-72 additionally validates hex format, because both parsers fall back silently.

- `TeamTheme.legibleOnDark` (DesignSystem.swift:79-98) measures against the composited control wash (`surface(for:over:)`), not an idealised background, and the comment records why the first version was wrong. `runTeamTintTests` (DesignSystemTests.swift:113-148) runs it over all 32 shipped teams and asserts the surface constants match the ones the palette tests declare. This is unusually careful work.

- No hand-rolled blur or glassmorphism anywhere. All 12 pinned control bars use the system `.background(.bar)` material (ArcadeFieldView, LiveGameView, DraftDayView, NewFranchiseWizard, ArcadeGameView).

- `Color.cardFill` and `Color.pageBackground` (DesignSystem.swift:244-261) resolve to `secondarySystemGroupedBackground` / `systemGroupedBackground` rather than hard-coded hexes, so the neutral chassis adapts correctly for free — the hex pairs in DESIGN.md's front-matter are documentation of what the system resolves to, not values baked into code.

- `monospacedDigit()` is applied consistently to changing figures — scores, clocks, cap hits, ratings, stat columns — honouring the Tabular Figures Rule.

- DESIGN.md's own "Known drift" section is accurate and complete on its own terms: the 44pt player-card font exists, and exactly two call sites (SeasonHubView.swift:188, LeagueViews.swift:198-199) pass a rating colour straight into Chip rather than through `.ratingStyle`. A doc that correctly tracks its own debt is worth keeping.

- Controls are overwhelmingly stock: Picker(.segmented), Stepper, Slider, Toggle, ProgressView, swipe actions, EditButton, alerts and sheets are used as-is throughout. TutorialView.swift:105 is the only hand-rolled control in the layer.

- Zero safe-area violations. `.ignoresSafeArea` appears nowhere in the UI layer, no content is placed under the Dynamic Island or home indicator, and every hero gradient band sits inside the navigation stack's content area rather than bleeding into the status bar. This is the single most common iOS slop and the app is clean on it.

- Icon set is 100% SF Symbols. All 38 distinct `systemName:` / `systemImage:` strings across the codebase are valid system symbols — no bundled image assets, no emoji, no mixed set. (One `●` text glyph at FrontOfficeViews.swift:88 is the sole exception and is filed above.)

- System materials, not hand-rolled glass. Every floating bar uses `.background(.bar)` (11 call sites); there is no manual blur, no fake translucency, no shadow anywhere in the system — consistent with DESIGN.md's Flat-Forever Rule.

- The arcade drag-to-aim gesture does not swallow any system gesture. ArcadeFieldView is presented via `fullScreenCover` (SeasonHubView.swift:53-59), which has no interactive dismiss to compete with, and the `DragGesture(minimumDistance: 0)` at ArcadeFieldView.swift:192-215 is confined to a field inset 10pt from the screen edge inside a fixed-height frame. No left-edge back gesture is disabled anywhere in the app — `navigationBarBackButtonHidden` does not appear.

- Correct modality choices. Self-contained sub-tasks are sheets (OfferSheet, NegotiationSheet, MatchupPreviewSheet, SkillTreeSheet, NewFranchiseWizard); the two immersive, must-resolve surfaces — the live game and Draft Day — are `fullScreenCover`. That is exactly the split the HIG describes, and it was clearly a deliberate call.

- One tint established correctly at the root. RootView.swift:20 injects the coached team's colour as the app-wide `.tint`, with TeamTheme.legibleOnDark (DesignSystem.swift:79-87) lifting dark-mode tints until they clear 4.5:1 against the composited control wash. Deriving the tint from game state through the environment is genuinely good architecture.

- Real platform controls where they matter. `Form` with `Stepper`, `Slider`, `Toggle` and `Picker` in OfferSheet and NegotiationSheet; `.pickerStyle(.segmented)` on the Season Hub and box score; `.swipeActions(edge: .leading, allowsFullSwipe: false)` plus `.onMove` plus a stock `EditButton()` on the depth chart (TeamViews.swift:169-215); `.alert` with correct `.destructive` / `.cancel` roles for releasing a player and exiting a franchise. The depth chart in particular is a well-built native list.

- Tab bar is used correctly: exactly five items, all of them sections rather than actions, each hosting its own NavigationStack so per-tab hierarchy is preserved. No custom global navigation anywhere.

- `EmptyStateView` is applied consistently — Injury Report, Draft Board, Hall of Fame, Trophy Room, News Feed, Schedule and Season Goals all have a real empty state with an SF Symbol, a headline and a sentence, rather than blank space.

- The franchise chassis — roughly twenty of the app's screens — is genuinely adaptive by construction. Every one is a `ScrollView` or `List` in a single column with token-driven padding (`Layout.medium`) and no fixed content width anywhere, so 375pt through 430pt all work without a single conditional. This is the thing that usually goes wrong and it is right here.

- Progress and meter bars use exactly the right pattern: `GeometryReader` for width inside an explicit small `.frame(height:)`, so they take their width from whatever container they land in and never assume a device dimension. TeamViews.swift:96–104, FrontOfficeViews.swift:60–70, ArcadeFieldView.swift:403–411, LiveGameView.swift:407–416.

- Horizontal overflow is handled deliberately wherever it exists rather than being allowed to clip: the position filters and stat categories are explicit `ScrollView(.horizontal, showsIndicators: false)` rows — FrontOfficeViews.swift:162, DraftDayView.swift:75, ArcadeGameView.swift:224.

- `TeamBadge` derives its glyph size from its own frame (`.font(.system(size: size * 0.32, …))`) and adds `.minimumScaleFactor(0.6)`, so the same component survives at 24pt in a standings row and 68pt in the team header without a second variant. NewFranchiseWizard.swift:284–291.

- The arcade's field-to-yards projection is fully proportional and shared by both the drawn routes and the aim gesture through one `fieldPoint` function (ArcadeFieldView.swift:224–235), with the release conversion using the same `size.height * 0.72` factor at line 211. The control mapping is therefore identical from SE to Pro Max — the genuinely hard part of making a touch game device-independent, done correctly, with a comment explaining why it lives in one place.

- No text field is trapped behind the keyboard. Every one sits in a `Form` or `List` (NewFranchiseWizard.swift:60, 105; LegacyViews.swift:53), so SwiftUI's automatic keyboard inset and scroll-to-focus handle it, and the wizard's action footer is a sibling of the scrolling content rather than an overlay, so it rides above the keyboard instead of under it.

- iOS-only presentation APIs are wrapped rather than force-fitted — `fullScreenCoverCompat` (SeasonHubView.swift:312–324), `navigationBarTitleDisplayModeCompat` (ArcadeFieldView.swift:484–494) and the `#if os(iOS)` around `EditButton` (TeamViews.swift:213) — each with a comment saying why.

## Appendix — Refuted Findings (6)

Raised by a finder, then killed by the verifier. Recorded so they are not re-raised.

**[Accessibility] CONFIRMED (item c): `.ratingStyle()`'s spoken tier cannot reach the user as designed inside a Button label**

The lines are as quoted (FrontOfficeViews:184-187 Text+ratingStyle inside a Button label; also 400-402, DraftDayView:256-259, TeamViews:233-236 consumed by the NavigationLink at 160-168), but the defect as described is not established. (1) The contract at DESIGN.md:166 is that the tier is set as an accessibility *value* "so the visible text ... is still read first" — it never promises "immediately after". Merging a Button label emits label-then-value, so the visible number is still read first and the tier still follows; the stated contract is met, not broken. (2) The claimed worse case — value dropped, leaving "colour as the only carrier" — contradicts the code: the rating digits are visible Text inside the merged label and are always spoken, and DESIGN.md:115 names "the adjacent number" as the non-colour carrier alongside the tier word, so colour is never alone regardless of what happens to the value. (3) The finding hedges between two opposite runtime behaviours and verifies neither; nothing in the source proves the value is dropped. This is speculation about SwiftUI merge semantics with no demonstrated user-visible loss. At most it is a P3 utterance-ordering nit. Note the genuinely verifiable version of this concern is the separate finding rating-chips-bypass-ratingstyle, which I confirmed.

**[Accessibility] Six text fields with no submit label, focus management, or keyboard dismissal**

The code facts are right — NewFranchiseWizard:62/107/108/137 and LegacyViews:54/55 are plain TextFields, and my own grep for FocusState/submitLabel/scrollDismissesKeyboard across Sources/ returns zero — but the described consequences do not hold, so no defect is demonstrated. (1) "The only way to dismiss it is to tap a row" is false: a single-line SwiftUI TextField resigns first responder on Return by default with no onSubmit, and a List's default `.automatic` scroll-dismiss behaviour dismisses the keyboard on drag, which is exactly the gesture a user makes to browse the 32-team list. (2) "A footer that the keyboard can cover" is false for this layout: the footer at NewFranchiseWizard:207-222 is the bottom child of the root VStack (23-37), and SwiftUI's keyboard safe-area inset lifts it above the keyboard. What remains is the absence of optional refinements (`.submitLabel(.search)`, focus management), which is polish with no user-visible failure — speculation dressed as a defect.

**[Performance] AppState reads the saves directory synchronously in its initializer, before the first frame**

REFUTED. The code is where they say — AppState.swift:46-49 calls store.list() in init, and RootView.swift:6 creates it as a @State initial value — but the stated defect does not hold. The claim's core is 'filesystem I/O on the launch path with nothing to show for it until the menu appears'; that is factually wrong. MainMenuView consumes app.saves on its very first frame: RootView.swift:88 and :90 for the Continue button's subtitle, :92 for its disabled state, and :171 for the load list. The work is a prerequisite for the first screen, not something done ahead of it. I measured SaveStore.list() at 0.28 ms. The remaining argument — 'unbounded in the number of saves' — is speculation about a hypothetical save count with no user-visible consequence, which is exactly the refutation criterion. Nothing here is a defect.

**[Platform Conformance] The three tab-root navigation lists are hand-rolled VStack+Divider stacks inside a card rather than inset-grouped Lists**

The structural facts are real (CoachViews.swift:20-61, TeamViews.swift:16-39, FrontOfficeViews.swift:13-30 are VStack+Divider stacks inside .card(), with row helpers at CoachViews:167-177, TeamViews:108-117, FrontOfficeViews:105-114), but the finding's premise is what DESIGN.md prescribes, not a deviation from it: Layout says "A single-column vertical scroll of focused cards", Components calls Card "The primary container for everything", and the chassis is described as "grouped backgrounds, white cards, generous whitespace, hairline dividers". DESIGN.md's stock-controls rule enumerates switch/segmented/stepper/picker/action sheet/alert/context menu/swipe actions — not List. Most claimed losses are also false: every row helper ends in `.contentShape(Rectangle())` (CoachViews:176, TeamViews:116, FrontOfficeViews:113) so full-row tapping works, Buttons and NavigationLinks still give press feedback, VoiceOver reads the rows normally, and the vertical padding is Layout.small on Dynamic Type text so heights do grow. The only verifiable residual is the separator inset mismatch, and even there the stated numbers are wrong — with the outer page padding at CoachViews:83 the text starts at 72pt from the screen edge and the divider at 84pt, not 56 and 68 (the 12pt delta is right; RootView:82/:94 is an 8pt delta in the same direction, not "the other way"). That alignment nit alone is P3, not a P2 architecture finding.

**[Platform Conformance] Bottom control bars use `.bar` material but stop short of the home indicator**

Refuted by the API. All four cited sites are real and are the last child of a full-height VStack (LiveGameView.swift:185 under the VStack at :82, DraftDayView.swift:216 under :18, NewFranchiseWizard.swift:221 under :23, ArcadeGameView.swift:185 under :30), but `.background(.bar)` resolves to `background<S: ShapeStyle>(_ style: S, ignoresSafeAreaEdges: Edge.Set = .all)` — Material is a ShapeStyle and the default is to ignore the safe area on all edges. Because each bar's bottom edge coincides with the bottom safe-area boundary, the material extends behind the home indicator while its content stays inset above it by `.padding(Layout.medium)` — precisely the system behaviour the finding asks for. No page-background strip appears. (The `.bar` panels that genuinely float are ArcadeFieldView.swift:299/349/388/416/435/449/466, which sit above `Spacer(minLength: 0)` at :91 — but those were not cited and the gap there is a layout choice, not a safe-area seam.)

**[Adaptivity] ArcadeGameView repeats the fixed-height non-scrolling column, in code that never renders**

Two grounds. (1) No user-visible consequence, which the finding itself concedes: I verified `grep -rn 'LiveGameView('` returns a single call site, SeasonHubView.swift:57, passing `arcade: false`; `isFinished` starts false (LiveGameView.swift:19); so the `arcade && !isFinished` gate at :25 is statically false and ArcadeGameView is never constructed. A defect in code that cannot render is not an adaptivity defect. (2) The stated mechanism is wrong. ArcadeGameView.swift:30-36 is `VStack { scoreboard; field; lastPlayCard; Spacer(minLength: 0); controls }` — the Spacer sits BEFORE `controls`, so controls are the bottom-anchored child, and the view has no `.frame(alignment: .top)` equivalent to ArcadeFieldView.swift:95. On overflow the collapsed Spacer leaves an oversized stack that centres in its parent and clips at both ends; the control block is not 'pushed past the bottom edge exactly as in ArcadeFieldView'. The cited line 126 (`.frame(height: 130)`) is accurate, but the described failure is not what this code would do.
