# Canonical AI-Generated Team Logo Set

**Date:** 2026-08-20

**Status:** Approved design

**Scope:** One original logo for each of the 166 teams in the canonical default-seed world

## 1. Purpose

Give every team in the canonical game world a memorable visual identity using an original, AI-generated sports logo. The set should feel at home beside American professional and minor-league sports identities without copying any real club's mark, character, lettering, league badge, or trade dress.

The logos are recognition marks. Team names, abbreviations, scores, status, and selection state remain available as text or existing semantic styling; no screen may rely on a logo alone to communicate essential information.

## 2. Product Decisions

- Produce one complete set of 166 logos for the world generated by `CoachWorldStore.defaultSeed`, currently `20_260_812`.
- Map each approved logo to the team's stable UUID. A team's display name or table position must never be the lookup key.
- Treat non-default seeds as unsupported by this first set. They continue to use the current colour-and-abbreviation identity rather than borrowing a canonical team's logo.
- Generate and curate the artwork before shipping it. The app performs no AI generation, network lookup, prompt execution, or image download at runtime.
- Use one primary mark per team. Secondary marks, uniforms, animated marks, and user-created logos are outside this scope.
- Allow unrestricted outer silhouettes. Logos may be freestanding, shielded, circular, irregular, character-shaped, or abstract.
- Keep the artwork free of words, initials, numerals, league names, and watermarks. The UI supplies team names and abbreviations separately.

## 3. Visual Direction

The set uses a **diverse American sports mix**, informed by official NFL, NBA, MLB, NHL, and Minor League Baseball identity galleries. The reference lesson is breadth rather than imitation: recognizable silhouettes, regional storytelling, mascots, objects, characters, framed crests, and abstract motion marks can coexist within one league world.

Each team receives one motif family chosen to keep neighboring and similarly named teams visually distinct:

- animal or creature mascot;
- regional landmark, natural feature, or local symbol;
- equipment, vehicle, tool, or culturally relevant object;
- original character or figure;
- shield, roundel, pennant, or other framed emblem;
- abstract speed, force, weather, or movement mark.

The family is a prompt constraint, not a mandatory container. A shield-family logo can break its boundary, while an animal can be a full figure rather than a head. No single family should dominate the finished contact sheet, and adjacent teams in the canonical ordering should not repeat the same family when a different treatment fits.

Every logo must:

- use the team's canonical primary and secondary colours as its main palette;
- remain recognizable at compact scorebug size;
- use bold, simplified shapes with a clean transparent surround;
- avoid fine detail that collapses when reduced;
- avoid photorealism, gradients that muddy at small sizes, and mockup effects;
- be visually original and not intentionally evoke a specific real team.

## 4. Source Manifest and Generation Workflow

A checked-in manifest is the source of truth for the set. It contains exactly one record for each canonical team with:

- stable team UUID;
- canonical team name and abbreviation, for review only;
- primary and secondary colour hex values;
- assigned motif family and team-specific concept;
- final generation prompt;
- asset name and source filename;
- generation status;
- human approval status and review notes.

The canonical world is exported once from seed `20_260_812` to populate the identity fields. Generation then proceeds one logo at a time so each output is independently replaceable. The shared prompt establishes the sports-logo finish, transparent background, small-size clarity, palette, text prohibition, and originality constraints. The team-specific prompt supplies the motif and regional story.

Each source image is a 1024 x 1024 transparent PNG. A generated image is accepted only after automated file checks and human visual review. Failed images are regenerated or edited individually; an accepted logo is never silently replaced by a later bulk run.

Human review covers:

- concept fit with the fictional team;
- legibility at compact, medium, and large sizes;
- unwanted text, watermarking, opaque background, or rendering artifacts;
- distinction from the other 165 marks;
- obvious similarity to real sports identities.

The final similarity and ownership judgment is deliberately manual. Automated checks can find duplicates and malformed assets but cannot provide legal clearance.

## 5. Asset Packaging

Approved PNGs ship in `Sources/ProFootballCoachUI/Resources/TeamLogos.xcassets`, processed as a Swift Package resource owned by `ProFootballCoachUI`, because that target renders the marks across screens. The package adds only the resource declaration required for the asset catalogue; no third-party image library or runtime asset service is introduced.

Asset names are recorded in the manifest and resolved through a static stable-ID catalogue. The catalogue returns `nil` for every UUID absent from the canonical set. It never guesses from team name, abbreviation, colour, or ordering.

The catalogue produces the existing `CoachWorldAssetReference` value. `CoachWorldReadModelProvider.teamReference(_:in:)` remains the single composition point that attaches the resolved reference to `CoachWorldTeamReference.mark`. The simulation's `TeamIdentity` stays unchanged, so saves and world generation require no migration.

## 6. UI Component and Data Flow

The app uses one reusable `CoachWorldTeamLogo` SwiftUI component:

- Input: `CoachWorldTeamReference` and a requested presentation size.
- Primary rendering: load `team.mark` from the UI package resource bundle with aspect-fit scaling.
- Fallback rendering: show the existing team-colour and abbreviation treatment when `team.mark` is `nil` or the named resource cannot decode.
- Accessibility: the image is decorative when the adjacent team name already labels it; otherwise the component exposes the team name. It never repeats a neighboring label to VoiceOver.

The complete data flow is:

`default world team UUID -> static logo catalogue -> CoachWorldAssetReference -> CoachWorldTeamReference.mark -> CoachWorldTeamLogo`

No view loads a raw asset name or performs its own UUID lookup. This keeps mapping, fallback behavior, and bundle selection consistent.

## 7. Placement

Logos appear where they materially improve team recognition:

- **Large:** team profile header and the controlled-team world identity strip.
- **Medium:** new-career job cards, world search results, rivalry detail, and ceremony/presentation surfaces.
- **Compact:** scorebug, standings, schedules, rankings, and roster headers.

The player-profile jersey number remains a jersey number; a logo may sit beside it but does not replace it. League-map markers remain accessible colour dots because the marks would be illegible at that scale and would clutter the map.

Existing product rules about team-colour restraint still apply. Adding a logo does not authorize opponent colour washes, new background treatments, or replacing semantic state colours.

## 8. Failure and Fallback Behaviour

- A non-default or unknown team UUID receives no canonical asset reference and renders the colour-and-abbreviation fallback.
- A missing or undecodable PNG uses the same fallback without crashing or leaving an empty layout hole.
- A malformed manifest, duplicate UUID, duplicate asset name, missing canonical UUID, or orphaned asset fails the validation check used during development and release preparation.
- Logos never block world creation, save loading, navigation, or match presentation.

## 9. Verification

### Catalogue and world checks

- Generate the canonical world from seed `20_260_812` and assert an exact 166-ID match with the manifest.
- Assert there are no duplicate UUIDs, duplicate asset names, missing records, orphaned assets, or accidental asset reuse.
- Generate at least one alternate seed and assert its teams receive `nil` marks and use the fallback.
- Test the central mapper so a canonical UUID receives the expected `CoachWorldAssetReference` and an unknown UUID does not.

### Asset checks

- Decode every PNG.
- Assert 1024 x 1024 dimensions and a usable alpha channel with transparent edge pixels.
- Produce a specimen grid showing all 166 marks at compact, medium, and large sizes on both light and dark surfaces.
- Compare files perceptually to flag exact or near duplicates for human review.

### UI checks

- Test the reusable component's asset and fallback branches.
- Capture representative screenshots for large, medium, and compact placements.
- Verify the affected screens at default and accessibility Dynamic Type sizes.
- Confirm VoiceOver announces each team once and that missing artwork does not remove the text identity.
- Confirm league-map markers and player jersey numbers retain their existing roles.

### Runtime boundary check

- Confirm the production app contains no AI-generation call, external image URL, prompt execution, or network dependency for team marks.

## 10. Acceptance Criteria

The work is complete when:

1. All 166 default-world teams have distinct, approved, original logo assets.
2. The manifest, stable-ID catalogue, and packaged assets match exactly.
3. Canonical teams show the correct logo through the central read-model path on every approved placement.
4. Alternate-seed, unknown, missing, and undecodable marks safely show the established fallback.
5. Compact-size, light/dark, Dynamic Type, and VoiceOver proofs pass.
6. The shipped app needs no runtime AI or network access for logos.
7. A human owner has completed the final originality and real-team similarity review.

## 11. Explicit Non-Goals

- Runtime or on-device logo generation.
- A logo editor or player-upload workflow.
- Logos for arbitrary seeds in this release.
- Secondary marks, uniforms, stadium art, league marks, or animated identities.
- Replacing the existing team colour system.
- A general-purpose asset framework beyond the existing `CoachWorldAssetReference` path.
- Automated legal clearance.

## 12. Reference Sources

Reference review used the official team directories for the [NFL](https://www.nfl.com/teams/), [NBA](https://www.nba.com/teams), [MLB](https://www.mlb.com/team), and [NHL](https://www.nhl.com/info/teams/), plus MLB's roundups of [new 2025 Minor League identities](https://www.mlb.com/news/minor-league-teams-new-logos-for-2025) and [new 2026 Minor League identities](https://www.mlb.com/news/new-minor-league-team-names-and-logos-for-2026). These sources inform the breadth of identity types and local-story approach only; production prompts must not name or request imitation of any real team.
